## 12 月 20 日前的学习安排

先以每周约 8–10 小时安排：工作日 5 次、每次约 60 分钟；周末安排 2 小时完整测评或专项训练，另用 90 分钟复盘。首次完整卷应使用未做过且来源可信的材料；App 内尚未导入合格整卷时可先使用官方在线测评。没有基线前不推算能否考到 650。

| 时间 | 重点 | 每周检查 |
| --- | --- | --- |
| 10/11–10/18 | 首次听读基线、找出时间不足和主要错因；熟悉导入与备份 | 听力/阅读各 100 题正确数、漏题、各 Part 用时；记录材料版本 |
| 10/19–11/08 | Part 2 短应答、Part 3/4 成组精听；Part 5 语法词汇、Part 6/7 依据定位 | 每天词汇约 10 分钟、听力 25 分钟、阅读 25 分钟；每两周一套新卷 |
| 11/09–11/29 | 弱项优先与阅读时间分配，逐步增加连续答题耐力 | 每周一套未做过的完整卷；复盘后重做单独标成复测 |
| 11/30–12/13 | 按考试时间完整模拟，复盘反复出现的错因 | 连续两次测评是否稳定、阅读剩余题数、听力失误原因；使用试卷自身有依据的参考分，不套用通用分数表 |
| 12/14–12/19 | 回顾高频错点、轻量复习、保持作息 | 不堆积新材料；安排一次设备/材料备份；不把软件升级变成考前负担 |
| 12/20 及以后 | 听读考试；考后再制定口语计划 | 记录真实成绩再调整下一阶段 |

每周据实际完成时间和陌生卷表现调整预算；若仍有大量漏题，先减少低收益新材料并解决时间分配。疲劳时可做最低 5 分钟练习，但不得记为完整训练或补造达标记录。

## 固定项目经理与发布机制

固定角色名为 `project_manager`，职责见 [项目经理职责](roles/PROJECT_MANAGER.md)。这是可接续的仓库角色，不是承诺后台永久运行的进程。每轮由主代理启动/复用这一职责，检查上次证据、范围和风险；无人在线时可继续开发与机器验证，需本人操作的验收记为待办。

每版发布必须有：变更范围与已知限制、测试报告、对应源码提交、Web 构建包、未签名 HarmonyOS HAP、SHA-256 校验文件、构建信息。GitHub 自带源码快照同时保留。个人设备签名调试包仅本地交付，不公开签名 Profile、设备标识或录音。公开 HAP 需由接收者自行配置签名后安装；不能称为所有手机可直接安装的商店包。

发布流程先完成检查与构建，再上传到草稿 Release、核验附件，最后标为 prerelease；任何门禁失败保留失败记录，不发布半套附件。已经公开的同一标签不覆盖产物，修复发新补丁版。源码上传、GitHub Release、Sites 部署及真机验收分开记录。

PR #33 增补的发布器检查读取所有已公开原生正式版/预发布，核对 build-info、标签对应源码的版本配置及 HAP 附件摘要；新 `versionCode` 必须高于历史最大值，在上传前、公开前各检查一次。沿用整条发布工作流的同一串行组；不能承诺阻止绕过 CI 的外部手工并发发布。历史 Web/源码版本不占原生升级号，缺失原生证据会阻止发布。同标签且源码及全部附件字节完全一致的重试只读通过；不会改写公开附件。当前 v0.3.0 是20006，下一个新版本至少20007，仍以发布时的历史最高值为准。

离线准备可同时传 `--previous-build-info` 与独立核验的 `--previous-build-info-sha256` 做提前检查；该文件不能证明线上最新状态，最终在线检查始终执行。相关 Node 和 Python 回归进入 Core/发布 CI。测试工具或文档变更不修改 release-manifest，不触发新 HAP、Web 或旧标签重发。
