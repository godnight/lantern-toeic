# RFC 0007：独立账号体系（邮箱验证码优先）

- 状态：提议，等待用户决策
- 提议日期：2026-10-20
- 关联：[RFC 0001](0001-harmony-only-platform.md)（平台范围，2026-10-20 用户再次确认只维护 HarmonyOS）、[RFC 0002](0002-phone-auth-and-online-data.md)（手机号路径保留为后续选项，本 RFC 取代其优先级而非其内容）

## 背景

当前服务端只信任托管层转发的 `oai-authenticated-user-id` 请求头作为用户标识（`lib/server-auth.ts`），账号体系因此存在三个确定问题：

1. **分发锁定。** Web/PWA 只有在 chatgpt.site 托管身份下才能登录同步；离开该托管层即没有账号。
2. **原生无法同步。** 鸿蒙原生端没有可信登录流程，记录只能保存在本机（`docs/ARCHITECTURE.md` 离线边界一节），换机或卸载即丢失——这是当前数据丢失风险最高的地方。
3. **身份与数据耦合。** D1 全部表以 ChatGPT uid 作为 `userId` 直接键入，未来任何身份变更都牵动全部历史行。

用户在 2026-10-20 明确"账号确实应该要改的"。本 RFC 给出方案与前置，不表示任何部分已经实现。

## 目标

- Web/PWA 与鸿蒙原生使用同一套自管账号登录，学习记录与录音跨端同步。
- 服务端不再把托管层请求头作为唯一身份来源；任何身份都必须由服务端校验的凭据解析。
- 现有 ChatGPT 身份下的学习数据可一次性迁移到账号，不丢首答、分钟与录音。
- 未接入真实邮件发送与会话校验前，任何界面不得标成已登录（沿用 RFC 0002 的诚实边界）。

## 推荐方案：邮箱一次性验证码 + 服务端会话

选择邮箱验证码作为第一种登录方式，因为它是唯一同时满足"Web 与鸿蒙都可用、无短信供应商前置、无平台生态锁定"的方案。

### 数据模型（全部为追加表，沿用只增不改的迁移纪律）

| 表 | 关键列 | 说明 |
|---|---|---|
| `accounts` | `id`（服务端生成的账号 ID）、`createdAt` | 学习数据的最终 owner；与任何登录方式解耦 |
| `auth_providers` | `provider`（`email` / `chatgpt` / 未来 `huawei`）、`providerUserId`、`accountId` | 身份到账号的映射；一个账号可绑多个身份 |
| `sessions` | `tokenHash`、accountId、过期时间、最近使用 | 只存散列；滑动续期；退出即删除 |
| `email_codes` | 邮箱散列、验证码散列、过期、尝试次数、发送冷却 | 6 位数字、10 分钟有效、错误上限后作废 |

### 流程

1. 输入邮箱 → 服务端生成验证码、散列入库、经邮件服务商 API 发送；按邮箱与 IP 分别冷却与每日限额，文案统一不泄露账号是否存在。
2. 校验通过 → 查找或创建 `accounts` 与 `auth_providers(email)` 映射 → 签发不透明随机会话令牌（只把散列写入 `sessions`）。
3. Web 端令牌走 `HttpOnly; Secure; SameSite=Lax` Cookie，并保留现有 `safeMutation` 来源校验；鸿蒙原生端走 `Authorization: Bearer`，令牌只存设备。
4. `/api/study` 与 `/api/recordings` 的身份解析改为：会话令牌优先，迁移窗口内兼容托管层身份头；解析结果统一映射到 `accounts.id`。保留 `x-lantern-owner` 期望用户检查，防止队列串号。

### 既有数据迁移（ChatGPT uid → account）

- 迁移窗口内，已认证的 ChatGPT 会话完成一次邮箱登录后，可执行"绑定并迁入"：写入 `auth_providers(chatgpt)` 映射，并以幂等批量作业把七张表的 `userId` 从 ChatGPT uid 改写为 `accounts.id`，逐表核对行数前后一致，重复执行结果相同。
- R2 录音对象键含旧 uid 路径，但 `objectKey` 逐行存储、路径仅为不透明标识，**不改对象位置**，避免大规模对象搬迁。
- 迁移完成前旧身份照常可用；迁移完成后两种身份解析到同一账号。不做行改写的"别名查询"方案被列为已拒绝：它让每次读取永久携带身份列表，复杂度留在热路径上。

### API 可达性（需在实现前确认的一个平台问题）

当前 Site 在托管层就是"仅所有者可访问"。邮箱登录接口必须能被未登录请求（含鸿蒙设备）到达，两个子选项：

- A. 托管层支持把站点改为公开、由应用层自己做登录门控（与 RFC 0002 记录的"所有者同意改成公开登录壳"是同一个决定）；
- B. 认证与数据 API 部署到独立的公开 Cloudflare Worker 域名，Web 同源之外、原生跨域访问，API 端配置 CORS 允许原生来源。

实现前需要所有者确认托管平台是否支持选项 A；不支持则走 B。两者不改变账号模型。

## 替代方案

| 方案 | 结论 |
|---|---|
| 维持 ChatGPT 身份 | 拒绝。分发锁定且原生永远无法同步，正是本次要解决的问题。 |
| 手机号短信（RFC 0002） | 保留为后续 provider。大陆短信需另行采购第三方服务并向 AGC 提供接口，前置成本高于邮箱；账号模型把手机号作为 `auth_providers` 新行即可接入，不需要重做。 |
| 华为账号 Account Kit | 列为第二阶段候选。鸿蒙用户体验最好，但 Web 端还需 Huawei ID Web OAuth，且把账号体系部分绑回单一生态；邮箱先行不阻碍后续接入。 |
| Passkey / WebAuthn | 暂缓。无发送成本但恢复与跨设备故事复杂，ArkWeb 支持度需真机核对；会话模型兼容后续追加。 |

## 影响

- 新增四张追加表与三个认证端点（请求验证码、校验登录、退出）；既有学习 API 只改身份解析入口。
- 客户端登录态、令牌存储与 401 后重新登录流程；鸿蒙原生新增登录界面与联网同步开关，离线本机能力不变。
- 词库 `vocabulary_events` 同样以 `userId` 键入，纳入同一迁移作业。
- 邮件服务商 API 密钥只进 Worker 秘密存储；验证码、令牌散列、邮箱散列之外不存明文，日志不记录完整邮箱。

## 外部前置（需用户完成，代码不能替代）

- 选择并开通邮件发送服务商（如 Resend / Amazon SES / 等价服务），把 API 密钥放入秘密存储；自定义发信域名（SPF/DKIM）可显著提升到达率，建议但非必需。
- 决定站点可见性（上述选项 A/B）。
- 真机验收环节的华为手机与本人账号操作。

## 验收

- 真实邮箱收到验证码；正确码首次创建账号、后续登录得到同一 `accounts.id`；错误、过期、频繁请求均失败且不泄露账号存在性。
- A/B 两个邮箱的数据、离线队列与录音完全隔离；退出后令牌立即失效。
- 迁移作业在含首答、复练、打卡、标记、资源任务、词库事件与录音元数据的测试数据上执行两次结果一致，行数与字段逐项核对；R2 对象位置不变。
- 鸿蒙真机完成邮箱登录、断网学习、恢复网络后幂等同步、换机登录读回记录；未验收前不宣称原生云同步完成。
- 仓库、构建产物与日志扫描不到密钥、真实邮箱或可复用验证码。

## 分工

| 工作 | 用户 | Codex |
|---|---|---|
| 邮件服务商 | 注册、计费、域名配置、密钥入秘密存储 | 给出设置步骤与非敏感配置检查 |
| 站点可见性 | 确认选项 A/B 与公开决定 | 按决定实现门控或独立 API 域名 |
| 迁移与验收 | 确认迁移范围、真机操作 | 表结构、端点、迁移作业、隔离与幂等测试、设备反馈修复 |
