# Main 20076 工程审计与界面改造建议

- 审计基线：`ca7127802abbec4d134b90f01cddd501fbb26e20`
- 范围：当前 `main` 的共享 React 界面、学习 Shell、版本事实、定向自动化与桌面 Chrome 合成账号场景
- 不在范围内：真实短信、生产云数据、真实用户数据、签名发布、HarmonyOS 真机 ArkWeb 验收
- 结论：**未发现本轮证据支持的 P0 学习数据或评分回归；主要债务是版本事实漂移、样式叠加和界面视觉层级。**

本报告区分“已复现”“静态风险”和“产品建议”。界面建议以可渐进落地的样式改造为主，不要求改变现有路由、学习状态或六主题结构。

## 二、版本与发布事实

### P1：版本号有多个互相矛盾的事实来源

基线中：

- `public/build-identity.json`：`versionName = 0.4.7`，`versionCode = 20076`
- `harmony/AppScope/app.json5`：`0.4.7 / 20076`
- `README.md:5`：仍写“当前交付 0.4.5 / 20059”
- 根 `package.json`、`release-manifest.json`、`mobile/package.json`、`harmony/package.json`：仍为 `0.4.6`

这不一定影响当前已构建制品，但会让审计、故障回滚和后续 PR 对“正在修改哪个版本”产生不同答案。

**建议改法：**

1. 明确唯一权威源，例如发布清单或构建身份信息。
2. 用脚本校验派生版本，而不是靠多处手工同步。
3. README 只展示当前已交付身份；源码包版本若语义不同，应明确解释，不要静默漂移。
4. 添加一个轻量测试，至少保证对外宣称版本、Harmony AppScope 和 build identity 一致。

### P2：架构文档的原生账号边界需要复核

`docs/ARCHITECTURE.md:25-27` 仍称原生默认 `owner=null`、尚无独立登录且未调用私有云 API。当前工程已经包含原生账号配置和登录相关实现。这里应依据当前启用条件、用户可进入的路径和真实部署状态更新，而不是简单改成“已支持云同步”。

建议分别写清：

- 未配置认证服务时的行为；
- 已配置服务时的登录入口和 owner 绑定；
- 哪些接口会跨端同步；
- 哪些数据仍只在本机；
- 当前验证到源码、构建、部署、设备中的哪一层。

## 三、Shell 与样式工程

### P1：全局样式叠加已经影响可维护性

`app/layout.tsx` 顺序加载七份顶层样式，`redesign.css` 还继续导入多份样式。`app/v041-app-redesign.css` 同时承担最终 Shell、今日任务、主题场景、弹窗修正和 vocabulary 触控补丁。

具体风险示例：

- `.v040-task-list` 与其他历史层反复改变任务究竟是边框列表还是独立卡片。
- 顶栏背景、查词显隐、标题字体和移动端正文边距依赖加载顺序与 `!important` 才能确定。
- `v041-app-redesign.css` 中“final presentation”“integration corrections”“today only”等补丁继续累积，后续换肤很容易在另一个断点产生遮挡。
- 六主题自动化能验证色值和基本几何，但不能证明视觉层级合理，也不能替代真机 ArkWeb。

**建议按依赖方向收敛，而不是再新增一份最终覆盖 CSS：**

```text
tokens（色彩 / 字阶 / 间距 / 圆角）
  → primitives（按钮 / 输入 / 列表行 / 分组卡片）
    → shell（顶栏 / 导航 / 内容宽度）
      → page（今日 / 单词 / 练习 / 复习 / 进度 / 发现 / 我的）
        → themes（只覆盖 token 与装饰，不改布局）
```

每次只迁移一个页面，删除被替代规则，并用同一组 390 / 940 场景回归。主题只更换色板与素材，不应各自实现另一套布局。

### P2：组件 API 与实际渲染不一致

`app/learn/workspace-shell.tsx` 中：

- `WorkspaceHeading` 接收 `eyebrow`、`description`，当前只渲染 `title`。
- `WorkspaceShell` 接收 `syncLabel`、`onSync`，当前未消费。

这不是已证实的运行时故障，但会误导调用方：调用者以为传入了说明或同步动作，界面却没有相应行为。

建议二选一：

1. 产品不需要这些信息：从类型和调用点删除，降低噪音。
2. 产品需要：补回可访问、可点击且有明确状态的 UI，并加交互测试。

## 四、界面审计：从“功能完整”到“安静、高端”

### 已观察到的现状

在 390px 的日间与空洞骑士实图中：

- 顶部装饰场景占据较大首屏高度，主学习行动被推后。
- 单词主卡、两个安排卡、顶栏和底栏同时使用明显边界，视觉噪声偏高。
- 两个今日任务在窄屏并排，长文案比单列分组列表更拥挤。
- 六个底栏入口权重相同，当前主任务不够突出。
- 题材主题素材本身完成度较高，但背景、描边、卡片和金色行动色会同时争夺注意力。

这不是要求马上删功能或改导航。第一阶段应保留所有入口和点击逻辑，只调整呈现。

### Kimi App 的可迁移设计观察

本次只通过用户手机上的真实界面截图与无障碍层级观察布局，**没有获得或声称获得其私有源码**。可迁移的是公开可见的设计原则：

- 近白中性色背景，浅灰胶囊，很少使用阴影和重描边。
- 首页只保留一个主要输入/行动区域，其余工具弱化。
- 设置页采用白色分组列表、细分隔线和稳定行高。
- 抽屉导航使用无卡片行，不为每个入口再套一层容器。
- 大留白、少常驻控件和一致的字体层级比复杂特效更重要。

不应照搬与托业无关的聊天输入框、AI 工具胶囊或品牌元素。

### 渐进改造方案

**阶段 A：不改变信息架构**

- 顶栏保留查词和“我的”，缩小品牌装饰权重。
- 今日页让“继续/制定单词计划”成为唯一高强调行动。
- 今日安排从双列卡改为单列分组列表；保留原按钮与路由。
- 减少卡片套卡片，用 1px 分隔线、12–16px 圆角和统一留白建立层级。
- 题材主题保留背景与配色，文字区增加稳定的中性表面，不让素材穿过正文。
- 默认日间使用近白背景，夜间使用柔和中性深灰；不要只做纯黑反色。

**阶段 B：逐页统一原语**

- 单词、复习、进度、发现、我的共用分组标题、列表行、主按钮、次按钮。
- “我的”采用账号摘要 + 设置分组 + 数据/关于分组，不新增平行页面。
- 保留当前六主题选择入口及所有主题资产。

**阶段 C：评估导航收缩**

六项底栏是否收缩为四个主入口加抽屉，应通过真实使用频率和点击路径评估。它不是本次样式 PR 的既成决策，不应与第一阶段混合提交。

### 两项基线失败的归因

1. `tests/short-word-audio.test.cjs` 的 `old-final-50ms` 负向控制失败：测试 mutator 使用 LF 字符串匹配，而 Windows checkout 的产品源码为 CRLF，导致替换前断言失败。正常产品路径的其余 32 项通过；这不是已证实的音频产品回归。
2. `tests/auth-test-preparation.test.mjs` 的实际 CLI 子进程失败：当前 Windows 托管 Node 入口需要 `ELECTRON_RUN_AS_NODE`，测试构造的最小环境未保留该执行模式，子进程未正常启动。不是认证准备逻辑拒绝了合法输入。

本 PR 对这两处测试可移植性做小范围修复，不修改产品音频或认证实现。修复后定向结果：

- `node --test tests/short-word-audio.test.cjs`：33 / 33 通过。
- `node --test tests/auth-test-preparation.test.mjs`：49 / 49 通过。
- 完整 `npm test`：内容校验通过，`test:study` 1031 / 1031 通过，生产构建通过，模块测试 89 / 89 通过。

### 验证边界

桌面 Chrome + 合成账号证明的是当前 Web 组件与受控 I/O 场景，不等于 HarmonyOS 真机 ArkWeb、短信供应商、云部署或签名 HAP 验收。私人手机截图和真实用户数据不进入仓库。

## 六、建议实施顺序

1. 合入两个测试可移植性修复，使 Windows 基线可重复。
2. 单独处理版本事实与架构文档，避免和视觉 diff 混合。
3. 样式 PR 先只改 Shell / Today / 我的，不改路由与学习状态。
4. 用相同合成数据做前后截图，覆盖 390、940、320、200% 字号、键盘焦点和全部导航点击。
5. 再逐页迁移其余模块；每次删除旧覆盖规则，不增加“最后一层补丁”。
6. 最后在 HarmonyOS 真机验证 ArkWeb 字体、安全区、音频、返回行为和主题对比度，再讨论发布。
