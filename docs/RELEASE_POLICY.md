# 分级验证与发布

按改动风险选择检查，不按版本号大小机械决定。一次按钮修改不自动变成全 App 验收。开发、测试、发布共同使用本页；历史阶段记录不追加当前门槛。

## 分支与版本发布

`main` 是目标产品主线：从已验收的 `main` 建立短期特性或修复分支，完成相应等级验证和用户要求的界面确认后，通过 PR 合入 `main`。小改走敏捷验证，不因需要合入主线而扩大到全量测试；未完成的工作继续留在特性分支，不算已发布。

目前 `main` 与 20075 发布线历史不同，20075 主体已在 `release/validated-20261023`，尚未合入 `main`。先核对两边历史、手机包实际构建源码与账号配置，再以保留历史和已有功能的方式完成整合；不得强推、直接覆盖或把不同历史误认为已合并。整合完成前从明确的已验收发布基线接续，并在交付中说明实际基线。

特性合并后核对远端、关联 PR 和分支独有工作；确认无未合并内容且不再使用后清理临时分支。清理前保留需要的历史和版本引用，不删除有独有工作、正在使用或用途不明的分支。分支数量定期整理，不长期保留每次测试或发布的临时分支。

按有意义的发布节点在已验收的发布提交打版本 tag 并创建 GitHub Release，说明实际包含的功能、验证范围和已知限制；不是每次小改都打 tag。用户明确指定本次不打 tag 时按该次要求执行；标签与发布不可替代 Web 部署或真机验收的实际结果。

## 用户确认的视觉范围

用户2026-11-02明确要求：换主题不得换布局。同一页面、视口和业务状态下，主题共用结构、内容顺序、控件位置及尺寸；主题仅调整配色、背景与装饰素材。任何可见修正仍须先展示具体方案并取得用户明确同意。

用户2026-11-01进一步明确：这一版界面固定后，所有显示界面的任何改动都须事先与用户显式对齐，并取得用户明确同意后实施；不仅限布局，也包括文案、颜色、透明度、图片、图标、状态、动效和可见行为。先提供具体变化与可审阅的前后效果；团队内部设计或测试确认不能替代用户同意。用户明确指定的变更按其授权的具体范围执行，超出该范围需另行确认。

用户2026-11-01明确要求：界面布局修改须由用户同意。仅调整页框透明度，不授权改变结构、位置、比例、导航或图片的显示与隐藏。实施前应让用户看到具体改动范围或前后对照；设计角色认可、QA通过均不能代替用户确认。用户已明确指定的改动和明确要求恢复的旧图、旧布局属于已授权范围，直接执行，不重复索要许可。新增主题素材先交候选供用户选择，未经确认不替换现有图片或顺带改版。


## 工程边界

| 层 | 主要位置 | 关注点 |
| --- | --- | --- |
| 展示与交互 | app/learn、components、CSS、主题素材 | 布局、阅读、点击、焦点、禁用状态 |
| 学习与业务 | lib、hooks、学习状态和评分逻辑 | 首答/复练、SRS、数据一致性 |
| 服务与存储 | app/api、db、drizzle、worker | 身份隔离、事务、迁移、托管媒体 |
| 原生适配 | harmony、mobile | ArkWeb、权限、生命周期、离线资源 |
| 内容与媒体 | content、public/audio、art | 修改内容的正确性、来源与播放 |
| 工程交付 | .github、构建/签包工具、docs | 可重复构建、明确版本和实际发布结果 |

不为分层移动已有业务文件。跨层依赖改变时提高验证等级；纯文档、版本号递增和交件元数据修正不自动提高等级。

## 四个等级

| 等级 | 例子 | 本次必做 | 默认不做 |
| --- | --- | --- | --- |
| L0 文档/流程 | 文档、说明、独立工具配置 | 文档一致性；工具改变时只跑受影响的工具测试 | 产品全测、Web/App 构建、签名、安装 |
| L1 局部界面 | 两个按钮、间距、页面文案 | 类型/相关组件检查；看实际改动页面；确认点击、必要的窄屏/大字号与焦点；构建需要交付的端 | PDF、整套考试/词典、音频全库、原生辅助工具矩阵、全页面截图 |
| L2 单模块功能 | 一个明确模块的缺陷修复 | 复现原问题、修复回归、相关边界与相邻接口；构建受影响端 | 未受影响模块重测、全量媒体重审 |
| L3 大版本/高风险 | 跨模块改造、身份/隔离、SRS、持久化迁移、原生桥、依赖/工具链更新 | 完整自动回归和相关端关键流程；新增风险的专项验证 | 给无关工具重签、多个角色重复扫同一包 |

CI 当前只对明确列出的文档、局部 UI、流程/签包工具和 Web 主题测试选择快速路径；普通业务模块尚未建立自动定向映射，仍保守走完整路径。未知路径或无法证明是纯版本元数据时保守走完整路径；分类失败必须报错，不能伪装为“文档无需检查”。main 与显式全量触发保留完整检查。用户声明的大版本使用全量入口。

PR 使用相对基线的累计差异，包括删除与重命名前后的路径。不能只看最后一笔提交，让早先未验证的业务变化被后续文档提交掩盖。小改以最近已验收基线建立短 PR，避免把一个旧的大 PR 无限续写；完成相关验收并符合用户已有授权后合并，未完成的改动不提前合并。

CI 的快速路径由 `.github/scripts/change-scope.mjs` 选择；签包工具入口见 [使用说明](../tools/harmony-release/README.md)。仅修改测试等待逻辑时，只验证该测试；工具测试通过不代表新 App 已验收。

## 账号相关验证

注册/登录、会话/退出、账号隔离、启动与入口路由、原生认证通信、账号服务地址/访问权限，以及影响登录的网络或生命周期发生变化时，同步补充并执行相关现有测试。纯词卡按钮、文案、间距等无关小改可继承最近已通过的账号结果，不增加全套账号回归；身份、隔离等高风险变化仍按 L3 执行。

- 基础流程：未登录时可见注册与登录入口；使用合成账号完成真实服务注册/登录并进入学习；退出后重新登录；错误密码、断网、超时、403 或非 JSON 响应明确失败，不能当作登录成功。
- 按实际风险补充：会话/生命周期变更验证冷启动、表单焦点、重复前台通知、后台恢复和重启；存储/隔离变更验证已有状态、同账号恢复及不同账号隔离。清空与已有数据场景分别记录，默认保留用户数据，只有当前明确授权时才清除。
- 正式手机交付：用待交付包、实际账号服务地址和手机真实网络做简短账号冒烟，确认注册/登录入口、成功登录并进入学习。模拟器通过、安装成功或版本正确均不能替代真机登录通过；403、入口不可用或不能进入学习记为失败/未完成。调试包可如实记录已知失败，不称正式可用。
- Web、模拟器、手机分别记录通过/失败/未运行或继承来源；在已有 PR/发布结果中注明源码/包版本、服务地址、设备与网络条件、实际覆盖和剩余问题，复用同一证据，不另建多层清单。

复用 `npm run test:auth` 及相关的 `tests/native-auth-client.test.cjs`、`tests/native-auth-host-v2.test.cjs`、`tests/native-owner-scope.test.cjs`、`tests/native-owner-lease.test.cjs`、`tests/account-ui.test.cjs`、`tests/browser/account-ui.cjs`。按实际变化选择并补充缺陷回归；这些本地检查不代替待交付环境的真实账号链路。

## 一次构建、按产物签名

- Web 改动只发布 Web 时，不构建或签 HAP。App 交付才构建 Shared 和 HAP。
- Web 托管构建与 App 离线构建是不同目标；每个需要交付的目标各构建一次，不在多个工作目录重复构建同一个目标。
- 只对最终可安装 HAP 使用原证书签名一次，并做一次官方验签。该次验签可以同时覆盖包签名和 code-sign，不拆成重复签名。
- Python、Node、Java、SDK、辅助脚本、source/Shared/Web ZIP 不需要用 App 证书签名。已有 SDK 和证书直接复用；工具或配置改变时才重新核对对应部分。
- sign 自身已有预检时，不再默认先独立执行 check 再 sign。check 是按需的 dry-run，不是每次发布的额外前置。
- 版本号、输出路径和制品身份作为请求参数传入稳定工具；不再为了 20058 → 20059 复制一套工具、重新跑整个工具矩阵。
- 正常 Shared 同步已核资源一致性时，不再紧接着完整 check:web。独立检查命令保留，供包被外部修改、传输异常或排障时使用。
- 原位升级保留数据；不为验收卸载或清空用户数据。设备回读版本和启动成功即可证明升级，不冒称逐条学习数据或全 App 已验。

## 共用一份结果

开发完成适用检查；独立复核只看本次变化及尚缺的证据；发布者引用同一结果。Git 提交与 delta 说明源码变化，最终制品记录一次 SHA；正常交接不重复遍历未变的全部音频、全部源码或每个工具。

一份 PR 说明或简短发布结果足够，包含：改了什么、等级和理由、实际做的检查及结论、源码/产物版本、已知剩余问题、发布/安装结果。不要层层生成 ENTRY → PINS → RECEIVED → CLOSEOUT 来互相证明。

未变模块可以继承原验证结果，明确标为“继承”，不冒称新跑。源码或产物实际改变才重做受影响检查；只修清单路径、父提交归属或文字说明，不重新构建或签名。

仅因具体差异、实际失败或新发现风险扩查，并说明原因。无关已知问题继续记录，不阻挡无关的小改发布。补充性的全量 CI 可以后台完成，不能把“仍运行”写成“已通过”，也不默认成为 L1 发布关卡；所选等级的必要检查仍需通过。

## 接续与协作

先读当前状态和本页，再读相关源码/角色。不要默认扫描全部历史记录、重新安装依赖、启动全套工具测试。依赖与锁文件未变化且已有可用环境时复用环境。

遵循用户已有授权：已授权的推送、发布和原位升级无需重复征求确认；真实运行时拒绝或缺少必要授权时如实处理。测试通过与用户视觉认可分别记录，不因此额外制造批准环节。

保持一个产品写入者、一个发布者；简单任务不安排多个角色重复相同核验。按上述发布节点创建 tag；签名材料、密码和服务凭据不得进入源码、命令行或交付说明。
